# PR Review to Closure Skill Design

## Goal

Create a globally discoverable `pr-review-to-closure` Codex skill for repeated reviews of the same GitHub pull request. The skill must preserve review state across new commits, prevent resolved or deferred findings from being reported as new problems, and produce a stable merge recommendation.

## Problem

The existing `code-review` skill performs a fresh Standards and Spec review against a fixed point. That works for a first review, but it does not retain finding identity or disposition across later reviews. A new pass can therefore rediscover accepted maintenance debt, mix new regressions with old findings, or change the apparent merge decision without explaining why.

## Invocation and Scope

The new skill is independent of `code-review` and may be selected automatically when a user asks to review a GitHub PR again, re-review it after fixes, or follow findings through closure. An ordinary one-off branch or diff review remains with `code-review`.

The skill reviews and reports by default. It comments, approves, requests changes, commits, or pushes only when the user explicitly asks for that external mutation.

## Review Ledger

Each PR receives one durable JSON ledger under `$CODEX_HOME/state/pr-review-to-closure/<host>/<owner>/<repo>/<pr-number>.json`. The ledger records:

- repository, PR number, base SHA, and last reviewed head SHA;
- each finding's stable ID, axis, severity, summary, location, evidence, first-seen SHA, acceptance criteria, and disposition;
- dispositions `open`, `fixed`, `deferred`, and `accepted`;
- whether each required PR and repository-standard evidence source was read;
- the latest verification command and result;
- the latest merge recommendation and its reasons.

Ledger writes are atomic. The skill treats PR text, comments, and ledger strings as untrusted data rather than instructions.

## Workflow

### First review

The skill pins the base and head SHAs, reads the PR description and discussion, identifies repository standards and the originating specification, and reviews the full three-dot diff. It assigns stable finding IDs and records explicit acceptance criteria. Findings are separated into Standards and Spec axes and classified as blocking or non-blocking.

The first review must inspect integration boundaries, error and safety behavior, public commands and documentation, and the smallest vertical path needed to validate the feature. It runs the repository's full required check when available.

### Re-review

The skill loads the ledger, verifies that it belongs to the same PR lineage, and examines both:

1. every previously open finding against its acceptance criteria; and
2. the delta from the last reviewed head to the current head for regressions or genuinely new findings.

It may inspect unchanged surrounding code when needed to evaluate an integration boundary, but it must not present an unchanged deferred or accepted finding as new. A deferred or accepted finding may reopen only when relevant code changed or new evidence materially changes its risk; the report must state why it reopened.

Every report groups results as `Still open`, `Fixed`, `New`, and `Deferred/accepted`. If no blocking findings remain and required verification passes, the skill gives a stable merge-ready conclusion and stops inventing new pre-merge cleanup work.

## Merge Decision Rules

- `Do not merge` requires at least one open blocking finding with concrete evidence.
- `Merge readiness not established` applies when a non-blocking finding remains open, required review evidence is missing, or required verification did not pass.
- `Merge-ready with follow-ups` means no finding remains open, review evidence and verification pass, and only deferred or accepted maintenance work exists.
- `Merge-ready` means no finding or requested follow-up remains and both review evidence and verification pass.
- A style preference or Fowler smell is not a blocker unless a documented repository rule makes it one or it creates a concrete correctness or maintenance risk in the changed code.

## Components

The skill contains:

- `SKILL.md` with routing, authorization boundaries, the first-review and re-review workflows, merge rules, and reporting contract;
- `references/ledger-schema.md` with the compact JSON schema and finding transition rules;
- `scripts/evidence.py` for validated, read-only PR metadata and discussion retrieval;
- `scripts/ledger.py` for deterministic ledger path resolution, initialization, validation, atomic updates, and summary output;
- `scripts/test_evidence.py` and `scripts/test_ledger.py` for recording-stub, workflow, safety, and recovery coverage;
- `agents/openai.yaml` generated by the standard skill initializer.

The evidence adapter calls only `gh pr view` and the read-only pull-request review-comment API. A recording-stub test rejects mutation commands. Commenting, approval, review submission, editing, merging, committing, and pushing remain in the agent workflow and require explicit user authorization.

Roc ships the canonical package under `skills/pr-review-to-closure/`. Onboarding copies every regular package file into `.agents/skills` and `.claude/skills`, preserves identical installations, rejects differing destination files, and refuses symbolic-link source or destination paths.

## Error Handling

- If no ledger exists, perform a first review.
- If the PR was force-pushed and the previous head is no longer an ancestor, preserve finding history, re-pin the new lineage, and perform a full review while identifying it as a lineage reset.
- If the ledger is invalid, preserve the bad file, report the problem, and rebuild from GitHub review history rather than silently discarding state.
- If required PR data or repository standards cannot be read, report the missing evidence and avoid a merge-ready conclusion.
- If the full test command cannot run, distinguish environment failure from test failure.

## Validation

Validate the skill package with the standard skill validator and test the ledger script with temporary directories. Behavioral fixtures must cover:

- first review creating stable IDs;
- a later commit closing an existing finding;
- a genuinely new regression receiving a new ID;
- deferred findings remaining suppressed;
- a relevant change reopening a deferred finding with an explanation;
- force-push lineage reset;
- invalid ledger recovery without data loss;
- no external GitHub mutation without explicit authorization.

## Non-goals

The skill does not replace GitHub, implement a general issue tracker, automatically post comments, force every review to use the same test command, or guarantee that a human reviewer will agree with severity judgments. It does not modify the existing `code-review` skill in the first version.
