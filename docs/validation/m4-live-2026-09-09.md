## Delivered behavior

- Safe diagnostics retain operational code, Issue, attempt and phase for worker
  and coordinator failures, including cleanup failures. Original private causes
  are excluded. Existing work and failed checkpoints remain available for recovery.
- Inspection and task details show elapsed, attempt and merge-wait time, recent
  checkpoint activity and incomplete usage. Missing or unreconciled historical
  timing is unavailable. Activity summaries add at most one checkpoint per 30 seconds.
- Comment reads use batches of four while preserving ordering, request count,
  complete history and authority checks. A failed batch drains fully and produces
  no partial snapshot.
- Explicit `skipScout: true` is available for approved low-risk tickets with
  concrete relative file paths. It is off by default. Implement and independent
  Review inspect the source themselves; no Scout output, attempt or usage is invented.

### Startup failure and recovery

The Scout-omission mode first failed during `gh repo view` startup preflight,
before any task claim or model attempt. That invocation took 33.56 seconds.
Including the failure and the coordinator's delay before restarting, the actual
trial took **12m 38s**. The successful-invocation table excludes that delay and
must not be read as proof of consistently shorter end-to-end waiting.

After this observation, preflight was changed to retry that read once on timeout.
A second failure stops with `GITHUB_REPOSITORY_UNAVAILABLE`. Write operations,
model roles and merges are not replayed. A deterministic regression covers the
retry bound, and an injected timeout followed by a real GitHub lookup confirmed
recovery. The model benchmark was not repeated after this later recovery fix.

## GitHub read measurement

Three sequential-read samples had a median of 7.467 seconds. Three samples with
four reads per batch had a median of 3.668 seconds, about 51% lower. Every sample
used 10 requests for the same 9 managed Issues and returned the same canonical
snapshot hash. This is a component-latency measurement, not a whole-task speedup.

## Verification and limits

The final repository check covers lint, type checking and 292 tests. Focused tests
exercise safe failure attribution, sibling isolation, cleanup ownership,
coalesced checkpoints, unavailable timing, bounded reads, explicit omission,
independent Review, refresh/re-review and unchanged merge guards. The public
`scheduler inspect` command also read timing and complete usage from real tasks.

Sandbox probes denied original credential reads and writes outside allowed paths.
All benchmark clients closed, no ownership lock remained, and isolated Pi,
home and temporary directories were removed. Worktrees and receipts were retained.
Network access remained enabled. This was one MacBook, not a VM or a two-host test.

There is one small task pair per mode. Model variation, caching, GitHub latency
and CI waiting limit generalization to larger tasks. The data establishes these
observed runs and unchanged acceptance outcomes, not a universal speed or token
reduction. Detailed evidence is in `.scratch/deliver-code/execution-efficiency/`.
